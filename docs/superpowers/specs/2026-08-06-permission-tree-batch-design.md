# 权限树批量设置设计规格

## 背景

当前权限设置页采用“角色列表 + 菜单表格 + 单菜单操作权限弹窗”的方式。管理员必须逐行打开弹窗修改操作权限，缺少整页全选、统一展开和一次保存能力。现有前端每次仅提交一个菜单条目，而后端 `PUT /rolemenu` 虽能处理多条 `detailList`，仍依赖正负数据库 ID 表示新增和删除，且相同内容重复保存会因 `SaveChangesAsync()` 返回 0 被误报为失败。

## 目标

- 左侧一次只选择一个角色，逐个角色配置权限，不支持多角色同时套用。
- 右侧以“业务模块 → 菜单 → 权限项”的树形结构展示当前角色的完整权限。
- 支持全选/取消全选、全部展开/全部折叠和一次保存整棵权限树。
- 后端提供语义明确、幂等、租户隔离的当前角色批量保存接口。
- 保留现有接口，避免影响已有调用方。

## 非目标

- 不增加多角色选择或权限模板套用。
- 不修改菜单表结构，不新增 `parent_id`；一级分组继续使用现有 `module` 字段。
- 不引入 Element Plus 或新的 UI 框架。
- 不改变登录、动态路由和业务页面按钮权限的消费结构。

## 方案选择

权限树使用项目已经安装的 Vuetify `VTreeview`，通过受控选择状态实现业务规则。该方案比继续改造 VXE Table 更接近属性树体验，也比自研递归树组件更少维护成本。页面沿用当前浅色主题、间距、圆角和主色，不照搬参考图的深色配色。

## 页面结构与交互

### 角色列表

- 左侧继续使用单选角色列表，任何时刻只有一个活动角色。
- 首次进入时自动选择第一个角色并加载权限。
- 当前角色存在未保存修改时，切换角色或刷新前弹出确认；确认放弃后再加载新角色，取消则留在原角色。
- 角色列表不增加复选框，不提供多角色批量入口。

### 权限树

- 一级节点：菜单 `module` 对应的业务模块。
- 二级节点：模块下的菜单。
- 三级节点：固定包含“访问菜单”叶子，并附加该菜单在现有 `actionDict` 中定义的操作权限叶子。
- 勾选模块或菜单节点时，选择其全部后代；取消时清空其全部后代。
- 勾选任一操作权限时，自动勾选同菜单的“访问菜单”。
- 取消“访问菜单”时，同时清空该菜单的全部操作权限。
- 仅勾选“访问菜单”是合法状态，表示可进入菜单但没有操作权限。
- 模块和菜单根据后代选择情况显示未选、半选或全选状态。

### 顶部工具栏

- “全选/取消全选”：对当前角色的完整权限树生效，并显示半选状态。
- “全部展开/全部折叠”：只改变展示状态，不改变权限草稿。
- 已选择菜单数量：仅统计已勾选“访问菜单”的菜单。
- “保存权限”：仅在存在活动角色、数据加载完成且草稿有变化时可用；保存期间禁用重复提交并显示加载状态。

### 保存反馈

- 保存成功后，以服务端返回结果重新建立基线，清除未保存状态并显示成功提示。
- 保存失败时保留当前草稿，显示后端错误信息，允许管理员修正或重试。
- 空权限树允许保存，含义是撤销当前角色的全部菜单权限。

## 前端数据设计

页面将完整菜单列表、角色已有权限和 `actionDict` 合成为展示树。树节点使用稳定字符串键，避免依赖数据库记录 ID：

```ts
type PermissionNodeKind = 'module' | 'menu' | 'access' | 'action'

interface PermissionTreeNode {
  key: string
  title: string
  kind: PermissionNodeKind
  menuId?: number
  actionCode?: string
  children?: PermissionTreeNode[]
}
```

键格式：

- 模块：`module:<module>`
- 菜单：`menu:<menuId>`
- 菜单访问：`access:<menuId>`
- 操作权限：`action:<menuId>:<actionCode>`

选中集合只以 `access` 和 `action` 叶子作为保存事实来源。构造请求时，仅输出已选择 `access` 的菜单；该菜单的 `menu_actions_authority` 由同菜单已选择的 `action` 叶子生成。提交前对操作码去重并排序，以获得稳定的脏状态比较和幂等请求。

权限树转换、选择联动、请求构造和脏状态判断应从页面组件中拆为纯函数或组合式函数，以便单元测试，不把复杂状态逻辑堆积在模板事件中。

## 后端接口设计

新增接口，同时保留现有 `PUT /rolemenu`：

```http
PUT /rolemenu/batch
Content-Type: application/json
```

请求体描述当前角色保存后的最终权限状态，不包含角色名称、数据库记录 ID 或删除标记：

```json
{
  "userrole_id": 1,
  "detailList": [
    {
      "menu_id": 10,
      "menu_actions_authority": ["save", "export"]
    },
    {
      "menu_id": 11,
      "menu_actions_authority": []
    }
  ]
}
```

响应继续使用项目统一的 `ResultModel<bool>`。没有数据变化也返回成功，保证重复提交幂等。

### 服务端处理规则

1. 校验 `userrole_id > 0`，`detailList` 不为 `null`。
2. 按 `currentUser.tenant_id + userrole_id` 校验角色存在，禁止跨租户修改。
3. 拒绝重复 `menu_id`，并校验每个菜单存在且对当前租户可见。
4. 操作码去除空白、去重并稳定排序；空数组表示只有菜单访问权限。
5. 按 `tenant_id + userrole_id` 加载现有权限，以 `menu_id` 为业务键计算新增、更新和删除。
6. 仅更新实际发生变化的记录；遗漏的现有菜单视为撤销权限。
7. 在一次 `SaveChangesAsync()` 中持久化全部变化；没有变化时直接返回成功。

现有数据库记录继续写入 `authority = 1`，并使用现有 JSON 字段保存 `menu_actions_authority`。本阶段仍以现有前端 `actionDict` 作为菜单操作项来源；后端负责格式、重复项和菜单归属校验，不新增菜单操作字典迁移。

## 兼容性

- 登录使用的 `GET /rolemenu/authority` 响应不变。
- `GET /rolemenu/all`、`GET /rolemenu/menus` 和 `GET /rolemenu?userrole_id=` 保持不变。
- 原 `PUT /rolemenu` 保留，新增页面只调用 `PUT /rolemenu/batch`。
- 原单菜单编辑组件先停止引用但不立即删除，避免不必要的范围扩张；确认无其他调用后可在后续清理。

## 错误处理与安全

- 角色不存在或不属于当前租户时返回失败，不执行任何写入。
- 任一菜单无效、重复或不可见时整批拒绝，不进行部分保存。
- 前端只在接口成功后更新基线；网络错误和业务错误均保留草稿。
- 批量接口不信任前端传入的角色名称、租户 ID、数据库 ID 或权限记录 ID。
- 所有查询与修改以当前登录用户的租户为边界。

## 测试策略

### 前端单元测试

- 按 `module` 构造三级树，并为每个菜单生成“访问菜单”叶子。
- 勾选操作权限时自动补选菜单访问权限。
- 取消菜单访问时清空该菜单操作权限。
- 全选、取消全选和半选状态正确。
- 请求只包含已授权菜单，操作码去重并稳定排序。
- 相同权限状态不标记为脏数据。

### 前端交互测试

- 一次只能选择一个角色。
- 展开/折叠不改变权限选择。
- 修改后切换角色触发放弃确认。
- 点击保存只发送一次 `PUT /rolemenu/batch`，并提交当前角色的完整最终权限状态。

### 后端测试

- 一次请求可新增、更新和删除同一角色的多条菜单权限。
- 空 `detailList` 撤销当前角色全部权限。
- 相同内容重复保存返回成功且不产生重复记录。
- 重复或无效菜单 ID 整批失败。
- 不能修改其他租户的角色或权限记录。
- 接口失败时不产生部分写入。

## 验收标准

- 权限页视觉上呈现清晰的模块、菜单和权限项树，不再使用逐行编辑弹窗。
- 当前角色支持全选/取消全选、全部展开/折叠和一次保存。
- 角色始终单选，权限不会被应用到其他角色。
- 保存请求不依赖数据库记录 ID 或负 ID 删除约定。
- 批量保存具备租户隔离、整批失败和重复提交幂等行为。
- 现有登录权限、动态路由和业务按钮权限行为保持兼容。
