# 实际装箱明细与负库存设计

日期：2026-08-28

状态：已确认（2026-08-28）

所属仓库：ModernWMS

关联 Handoff：`b117e2b0-c592-4fac-af72-a580c0b45a63`

## 1. 目标与边界

本阶段只解决“实际装箱事实如何落库并据此结算库存”的问题：

- 装箱任务的商品、SKU 和计划数量只作为操作参考，不作为实际装箱上限。
- 装箱人员填写的每箱实际商品、实际库存来源和实际数量是最终业务事实。
- 允许少装、多装、增加任务外商品、使用任务创建人或其他货主的库存。
- 库存不足不阻断装箱、称重和出库；可用量、总量和库存分配量允许形成负数。
- 发货后原出库不可回退。发生拦截时，按实际拦截回来的数量另行入库，不改写原出库记录。
- 本阶段不新增“SKU 差异审计表”，也不把计划与实际不一致作为阻断条件。

本设计不执行生产数据迁移，不触碰生产环境。Flyway 迁移只允许在已核实为开发环境、数据库名为 `ruoyi-vue-pro` 的目标执行。

## 2. 事实模型

系统区分两类数据：

直接升级现有 `wms_weighing_box_item`，使它成为装箱人员保存和确认的箱内实际库存明细。装箱任务计划继续由 `wms_dispatch_packing_task_item` 保存，不再单独维护一套箱内计划分布，也不新增实际装箱表。

实际明细表不是差异表，也不是事件日志。它回答：哪一个箱子实际装了什么 SKU、用了哪一笔库存、属于哪个货主、数量是多少。

建议结构：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | 主键 | 实际装箱明细 ID |
| `weighing_box_id` | 非空外键 | 所属箱子 |
| `client_line_key` | 非空 | 前端生成的稳定行键，用于保存幂等 |
| `packing_task_item_id` | 可空外键 | 可选的计划商品引用；任务外商品为空 |
| `wms_sku_id` | 非空外键 | WMS SKU |
| `erp_stock_id` | 非空 | ERP 库存主记录 |
| `stock_allocation_id` | 非空外键 | 实际使用的 WMS 库存分配行 |
| `goods_owner_id` | 非空 | 实际库存货主快照 |
| `goods_location_id` | 非空 | 实际库位快照 |
| `sku_code` | 非空 | SKU 编码快照 |
| `commodity_name` | 非空 | 商品名称快照 |
| `actual_qty` | 正整数 | 本箱实际使用数量 |
| `dispatchpicklist_id` | 可空外键 | 实际确认后对应的出库拣货明细 |
| 审计字段 | 非空 | 创建人、创建时间、更新时间、版本号 |

改造约束与索引：

- 删除原唯一键 `(weighing_box_id, packing_task_item_id)`，允许一个箱子中的同一计划商品使用多条库存。
- 新唯一键：`(weighing_box_id, client_line_key)`。
- 索引：`packing_task_item_id`、`stock_allocation_id`、`dispatchpicklist_id`。
- `actual_qty > 0`。
- 一条实际明细只能指向同仓库中一条有效的库存分配行。

原 `task_qty` 列改名为 `actual_qty`。现有开发测试数据无需保留或回填业务含义；迁移后由装箱人员重新保存实际明细。

`packing_task_item_id` 只用于说明“它与哪条计划有关”，不决定 SKU、货主或数量。SKU 身份由实际选中的库存分配行校验并落快照。该表是唯一箱内实际事实源，不是差异表或审计表。

## 3. API 与页面行为

保存箱子时同时提交 `inventory_items`：

```text
client_line_key
packing_task_item_id（可空）
stock_allocation_id
actual_qty
```

后端根据 `stock_allocation_id` 读取并固化 SKU、ERP 库存、货主、库位等字段，禁止由前端伪造这些身份字段。

实际库存选择接口按当前仓库返回有效库存分配行：

- 不限制为装箱任务原商品。
- 不限制为任务创建人的库存。
- 不以可用库存大于零作为查询条件。
- 返回当前可用量和可能形成的负库存提示，但提示不阻断保存和确认。

只有以下情况阻断：

- 箱子、库存、SKU 或库存分配行不存在。
- 库存分配行已停用或不属于当前仓库。
- 实际数量不是正整数。
- 请求版本冲突或幂等键冲突。
- 提交的身份与服务端查到的库存身份不一致。

计划量不足、计划量超出、SKU 不同、货主不同、库存可用量不足都不阻断。

## 4. 实际确认与预占结算

首次选择库存时，仍按“装箱任务量 × 变体数量”建立计划预占。确认实际装箱时，以所有箱子的实际明细聚合结果替换计划预占目标：

- 实际量小于原预占：释放差额。
- 实际量等于原预占：保留已有预占。
- 实际量大于原预占：在实际库存分配行追加预占，允许库存变负。
- 实际包含任务外商品：建立对应出库明细、拣货明细和预占关联。
- 原计划库存实际未使用：释放其剩余预占，并从最终出库明细中移除。

确认事务内完成：

1. 锁定装箱任务、箱子、实际明细、相关预占与库存分配行。
2. 校验版本、稳定业务键和实际库存身份。
3. 按实际明细聚合目标量。
4. 释放多余预占、增加不足预占并建立任务外商品关联。
5. 物化最终 `dispatchlist` / `dispatchpicklist`，写回 `dispatchpicklist_id`。
6. 更新实际确认状态并提交事务。

任何一步失败整笔回滚。相同 `request_id` 和相同业务指纹重放时直接返回原结果，不得重复预占或重复形成负库存。

## 5. 负库存规则

保留数量守恒：

```text
库存总量 = 可用库存 + 预占库存
预占数量 = 已消费数量 + 已释放数量 + 剩余预占数量
```

调整非负约束：

- `trk_stock.available_qty` 可为负。
- `trk_stock.total_qty` 可为负。
- `trk_stock.occupied_qty` 必须大于等于零。
- `wms_erp_stock_allocation.allocated_qty` 可为负。
- `wms_erp_stock_allocation.occupied_qty` 必须大于等于零。
- 允许 `occupied_qty > allocated_qty`，它表示该库存分配行已经产生库存欠账。
- 预占分配表中的预占、释放、消费、剩余数量仍必须是非负数并保持生命周期守恒。

例：某库存可用 480、预占 480，实际需要 500。追加 20 预占后可用为 -20、预占为 500、总量仍为 480；出库消费 500 后，可用仍为 -20、预占为 0、总量为 -20。后续真实入库 20 后自然归零。

库存流水和分配流水必须保存负数前后值、操作者、业务键、命令 ID 和来源实际装箱明细，使欠账可追踪，但不额外建立 SKU 差异审计表。

## 6. 出库与拦截

`SHIP_OUT` 只消费实际确认后物化的出库/拣货明细：

- 出库数量以实际装箱明细为准。
- 出库可以使库存总量和库存分配量为负。
- 成功出库后原事件永久保留，不允许反向修改、撤销或恢复原库存。

拦截是新的入库业务：

- 实际拦截回来多少，就新增加多少库存。
- 可以少于原出库量，也可以分批入库。
- 拦截入库关联原出库用于追踪，但不改变原出库状态和数量。

拦截入库的完整业务实现不属于当前切片；当前切片只确保原 `SHIP_OUT` 不再设计回退入口。

## 7. Flyway 迁移

采用前向迁移，不修改已执行迁移文件：

1. 原位升级 `wms_weighing_box_item`：`packing_task_item_id` 改为可空，`task_qty` 改名为 `actual_qty`，增加实际库存身份、快照、幂等行键和最终拣货明细引用。
2. 删除原 `(weighing_box_id, packing_task_item_id)` 唯一键，增加 `(weighing_box_id, client_line_key)` 唯一键和实际库存查询索引。
3. 删除 `wms_erp_stock_allocation` 中禁止 `allocated_qty < 0`、禁止 `occupied_qty > allocated_qty` 的检查，保留 `occupied_qty >= 0`。
4. 对 `wms_erp_stock_allocation_log` 删除禁止负分配量及 `occupied <= allocated` 的组合检查，新增只约束前后 `occupied_qty >= 0` 的检查。
5. 不创建任何新表；开发测试数据允许清理或转换，生产环境不执行本迁移。

执行保护：

- 执行前再次查询 `DATABASE()` 并确认严格等于 `ruoyi-vue-pro`。
- 记录 Flyway 校验、迁移版本和执行结果。
- 不连接、不探测、不修改生产环境。
- 不把数据库地址、用户名或密码写入迁移、文档、日志或 Git。

## 8. 锁序、业务键和幂等

统一锁序：

```text
装箱任务
-> 称重箱（按 ID）
-> 实际装箱明细（按 ID）
-> 预占主单/分配（按 ID）
-> ERP 库存（按 ID）
-> WMS 库存分配（按 ID）
-> 出库明细/拣货明细（按 ID）
```

稳定业务键不得使用时间戳、当前行数或 `COUNT(*)`：

- 实际行：`packing-task-id + box-id + client-line-key`。
- 确认命令：`packing-task-id + request-id + action`。
- 库存流水：`confirm-command-id + stock-allocation-id + mutation-type`。
- 出库明细：`packing-task-id + actual-line-id` 或其确定性聚合键。

业务指纹至少包含箱子、实际行键、库存分配行、数量和版本。相同请求 ID 但指纹不同必须报冲突。

## 10. 跨仓影响

- `ruoyi-vue-pro`：共享 `trk_stock` 与预占数据，必须理解负库存语义，但当前 ModernWMS 对话不修改该仓库，也不新增 WMS 调用 Ruoyi API。
- `yudao-ui-admin-vue3`：若 ERP 页面目前假定库存非负，后续由独立任务调整展示，本切片不修改。
- `fbashipment-sync`：只能消费已完成的出库事实，不得回写或回退 WMS 出库；当前不修改。
- `xxl-job`：当前无代码变更，只需确保后续任务不把负库存当作自动回滚条件。

如其他仓库需要修改，必须另建对应仓库 Handoff，由用户转达；ModernWMS 当前实现不得跨 Git 根写入。
